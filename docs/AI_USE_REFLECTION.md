# VisRef 재현: AI 활용 반성 기록 (2026-10-12)

한 줄 요약: AI(Codex, Claude, 하위 에이전트, 외부 AI 도구)가 논문·로그를 읽고 확인 없이 단정하거나, 사용자 결정을 놓치거나, 검증되지 않은 가정 위에 다음 결정을 쌓아서 방향이 틀어진 일이 여러 번 있었다. 가장 큰 것은 사용자가 정한 "Z = 마지막 층"이 코드 재작성 때 사라진 일과, "채운 토큰은 관련성 순서일 것"이라는 틀린 가정 때문에 그 실험이 미뤄진 일이다.

## 범위와 확인 수준
- 대상: 실험 기록 `docs/EXPERIMENT_FLOW.md`(EF) 전체, 출처 대장 `docs/SPEC_LEDGER.md`, 독립 감사 `docs/AUDIT_REPORT_20261007.md`, `repro/audit/`의 검토 기록, `REPORT.md`, 2026-10-12 공개 문서 정리 세션.
- 방법: Sonnet 하위 에이전트가 전체를 훑어 후보 74건을 찾았다(범주별 집계는 하위 에이전트 값, Claude 미대조). 아래 본문에 쓴 사례의 근거 줄 57곳은 Claude가 원문과 대조해 모두 일치를 확인했다(인용 문구가 표시한 줄 ±2줄 안에 있음). 줄 번호는 이 저장소 `docs/` 파일 기준.
- 오류로 세지 않은 것: 가설이 실험에서 기각된 것 자체(fill, step1_branch의 무효 결과), fp16 잡음 같은 모델 특성. 그 결과를 과장해서 쓴 문장은 오류로 셌다.

## 1. 사용자 결정이 코드 재작성·인계 과정에서 사라졌다
- **Z(생각 단계 벡터) = 마지막 층**: 2026-10-06 사용자가 "입력 임베딩이 아닌 last hidden state가 타당하다"고 정해 우선 후보로 지정했다(EF L501). 10-07 새 코드(`repro/`)를 쓸 때 기록된 사용자 결정 (1)–(4)에 Z가 없었고(EF L750), 입력 임베딩으로 구현됐다. 그 결과 본 실험 1,000문항과 후속 실험이 모두 입력 임베딩 Z로 돌았고, m의 약 1/5만 주입되는 문제의 원인이 됐다. 마지막 층 Z는 10-12에야 `visref_hs`로 사전등록됐다(EF L1659~). 10-13 결과에서 주입 수는 m에 도달했지만 TSR 대비 추가 이득은 없었다(hs − TSR +0.24 pp, 95% CI −2.38 ~ +3.10, 사전등록 판정 ③). 빠진 결정 하나를 되살려도 논문 크기의 이득은 나오지 않았다.
- **결정이 바뀌었는데 코드 기본값은 옛 값으로 남았다**: `run.py`에는 실행 인자를 주지 않을 때 쓰는 기본값이 있다. 각 실행에 묶어 보낸 코드를 열어 보면, 생각 상한 기본값은 smoke·smoke2 때 단계 8,192 / 합계 16,384였고, 10-07 사용자 결정(단계 4,096 / 합계 8,192, EF L804) 뒤의 실행(full_s1, smoke3 등)부터 그 값이었다. 같은 날 단계 1,024 / 합계 10,240은 b_test의 변형 설정으로 시작해(EF L859) 실행 인자(`--think-cap 1024 --total-think-cap 10240`)로만 넘겼고, 이 값이 본 실험 설정이 된 뒤에도(EF L952-956) 기본값은 4,096 / 8,192로 남았다. 실제 실행(b_main 9개 세션, fill, diag_st_plain)은 시작 로그에 1,024 / 10,240이 찍혀 있어 결과는 영향이 없고, `visref_hs`도 실행 인자에 같은 값이 있다(Claude가 실행 묶음 코드와 시작 로그에서 직접 확인). 하지만 인자 없이 `run.py`를 돌리면 결정과 다른 옛 값으로 동작했다(10-13 기본값을 1,024 / 10,240으로 정정). 기존 테스트는 자체의 작은 설정을 써서 이 차이를 잡지 못했고, 10-12 결정 점검에서야 발견했다(EF 2026-10-12 "결정 점검", SPEC_LEDGER 결정 대장 J-10).
- **순서 지시 무시**: TSR 정지 엔트로피를 실제 모델로 검증하기 전에 DPP를 먼저 구현했다(사용자 지적, EF L684).
- **설명 없는 설정 변경**: 사용자가 재확인한 누적 14k 기준을 R26에서 8192로 바꾸면서 미리 설명하지 않았다(EF L690). R26은 7,200초를 청구받고 표본이 비었다(EF L705).
- 반성: 코드를 새로 쓰거나 세션을 넘길 때, 이전 "사용자 결정" 목록 전체를 새 설정과 한 줄씩 대조하지 않았다. 결정이 빠지면 빠졌다고 적어야 했다. 또 결정이 바뀔 때 코드 기본값은 그대로 두고 실행 인자로만 새 값을 넘겨, 결정 값이 코드에 남지 않았다.

## 2. 검증하지 않은 가정 위에 다음 결정을 쌓았다
- **"채운 토큰은 관련성 순서"**: 합성 데이터에서 εI 채움이 관련성 순서처럼 보이자(EF L1069) "계수 이후 관련성 채움이 가장 자연스러운 후보"라고 썼다(EF L1070). 독립 설계 검토는 "단정하지 말고 Spearman으로 실제 확인하라"고 경고했다(`repro/audit/design_review_variants_20261010.md` L58). 그런데도 "은닉 상태 Z와 채움은 실질적으로 같은 개입"(EF L1049)이라며 "별도 실행 불필요"로 결정했다(EF L1287). 실제 fill 실행에서 채운 순서와 관련성의 순위 상관은 −0.10이었다(EF L1488). 결과적으로 약 11.3시간 세션(EF L1438)이 "관련 토큰 m개" 질문을 시험하지 못했고, 마지막 층 Z 실험도 미뤄졌다.
- **"주입은 이어갈 때만 일어난다"**: 틀린 보고가 며칠간 주입 통계와 해석의 전제였다(EF L1022에서 정정).
- **자연 종료 뒤 H 중앙값 0.003–0.007**: 실제 값은 1단계 전체 중앙값이었고 자연 종료만은 2.4e-5 / 5.8e-5였다(EF L1515). 이 값이 "다중 표본으로 바꿔도 멈출 것"이라는 예상의 근거로 쓰였다.
- **native ST = 논문 ST**, **"별도 최종 답 생성은 논문에 없다"**: 둘 다 틀려 정정했다(EF L441, L662).
- **"같은 시드라 첫 단계는 같다"**: fill 결과에서 첫 단계가 끝난 방식의 일치율(874/976)만 보고 나머지를 "1단계 재생성의 fp16 배치 잡음"으로 적었고(EF L1444), `visref_hs` 사전등록에도 "같은 문항별 시드라 첫 단계는 fp16 배치 잡음 범위에서 같다"고 썼다(EF L1664). 텍스트를 직접 비교하지 않았다. 실제로 첫 단계 텍스트가 본 실험과 같은 문항은 `visref_hs` 839개 중 193개, fill 994개 중 242개였다. 그래서 "Z만 다르다"는 설명이 틀렸고, 짝 비교의 불일치가 사전등록 가정 9%의 거의 두 배(16%)가 되어 +3.5 pp를 잡아낼 확률이 약 72%로 낮아졌다. 판정 자체는 실제 데이터로 계산한 CI라 유지된다. 2026-10-13 독립 검토가 찾았다.
- 반성: 다음 결정을 내리는 데 쓴 가정은 "검증됨 / 미검증"을 표시해야 했다. 특히 미검증 가정을 근거로 "실행 불필요"를 결정하면 안 된다.

## 3. 논문·코드·로그를 읽고 확인 없이 단정했다 (가장 흔함)
- 공식 점수 59.3 / 69.5를 "thinking 끔 / 켬"이라고 설명했다. 근거가 없었다(EF L1095 철회).
- 출처 대장에 "본문·부록에 추정법 서술 없음", "수식은 log만 쓴다"고 썼다. 감사에서 틀린 것으로 지적됐다(AUDIT L56, L63). 논문 부록 G는 다른 식에 "natural logarithm"을 쓴다(`VisRef_layout.txt` L944).
- top-k·top-p 근거로 든 모델 페이지 줄이 사고 모드 권장이 아니었다(AUDIT L59). 출처 대장에 "인용 구현에서 확인"이라 쓴 항목도 과했다(AUDIT L54).
- 강제 답 방식이 "s1·DEER와 같은 형식"이라고 썼지만 어느 참고 문헌과도 같지 않았다(EF L889).
- InternVL3-1B를 대안 모델로 올렸다. 근거는 수치 근접 하나였다(AUDIT L58). 10-12 사용자 지적으로 삭제했다.
- 2026-10-12 공개 문서 정리 중에도 반복됐다(2026-10-12 세션의 Claude):
  - H 추정을 바꾼 이유를 "비용이 커서"라고 썼는데, 기록에 없는 이유였다.
  - 그 경위의 순서도 거꾸로 썼다. 실제는 처음엔 답 하나, 참고 문헌을 보고 다중 표본 시도, 다시 답 하나였다(EF L1639, 사용자 지적).
  - 태그를 붙인 주입을 "시험하지 않음"이라고 썼지만, 실제로는 10-07에 시험했다. 형식이 깨져서 태그를 뺀 것이었다(EF L1653).
  - "MathVista는 모든 답을 LLM으로 추출한다"고 썼지만 틀렸다. 단순한 응답은 규칙으로 처리한다.
  - "사고 모드 켜는 법"을 논문에서 찾지 못한 설정에 넣었지만, 논문은 사고 모드 사용을 밝힌다.
- 2026-10-13 독립 검토(작업을 보지 않은 상위 모델)가 찾은 것:
  - 지표의 부호를 정의와 반대로 읽었다. REPORT 4.5절에 마지막 층 Z의 뒤쪽 선택이 "관련성과 약하게 반대"(−0.171)라고 썼지만, 지표 정의는 "음수 = 관련성 큰 것이 먼저"였다(`repro/visref/dpp.py` L107-108). 실제 뜻은 "약하게 관련성 순"이다. 같은 날 정정했다.
  - 공식 InternVL3.5-1B 59.3을 "사고 모드인지 보고서에 없다"고 썼다(2026-10-10 판단, EF L1094). 보고서는 Section 3 수치를 사고 모드를 포함한 TTS 없이 얻었다고 밝힌다(`InternVL3.5.txt` L556-562). 같은 날 정정했다.
- 반성: 원문 줄을 확인하기 전에는 "미확인"으로 써야 했다. 공개 문서에 넣는 문장일수록 그 자리에서 근거 줄을 다시 열어 봤어야 했다.

## 4. 결과를 실제보다 강하게 썼다
- "재현됨", "사전등록"을 실제보다 강하게 썼다. 주 비교는 392문항, CI 분류 규칙은 759문항 중간 결과를 본 뒤 고정했다(EF L1604).
- fill 결과를 "m개를 넣어도 이득 없음"으로 읽히게 썼다. 실제로는 관련성과 무관하게 채운 변형의 결과였다(사용자 지적).
- `Final Answer:` 진단(150문항)을 "차이를 만든 것은 아님"이라고 단정했다. 실제 95% 범위는 약 −9.5 ~ +5.5 pp였다(EF L1654).
- 초안에 "주입 효과 0"이라고 썼다. 실제로는 15 대 14였다(EF L1424).
- "이미지가 즉답에서 도움 → 이어가기 뒤 사라짐"이라는 인과 단정은 과했다(EF L1520).
- "ST의 57%가 상한(반복 루프)"이라고 썼다. 실제로 루프는 절단의 약 절반이었다(EF L1319).
- 반성: 해석 문구는 CI와 검출력 범위 안에서만 써야 했다. "차이 없음"은 "이 표본으로는 몇 pp 이하를 가려낼 수 없음"으로 써야 했다.

## 5. 자율 실행 범위와 검증 기준이 지나쳤다 (주로 Codex 자율 구간)
- 논문 baseline을 검증하기 전에 개선 실험부터 진행했다(EF L46). 공식 Thinking 프롬프트도 빠져 있었다(EF L25). 이 기간의 300행과 155/1,800행 결과는 근거로 쓰지 못하게 됐다.
- 수치 일치 기준을 지나치게 엄격하게 두었다. 사용자가 검증 기준이 과도하다고 지적했다(EF L622). R22(GPU 2,526.896초, EF L587)는 GATE_FAILED였고, 그 원인을 찾느라 R23(906.493초, EF L607)이 이어졌다.
- 이 구간의 누적 GPU 사용은 R29 시점에 50,981.329초였다(EF L758). 같은 구간의 기록은 논문 재현이 검증되지 않았다고 스스로 적고 있다(EF L705). 다만 이 중 어디까지가 낭비였는지는 기록에 없다.
- 반성: 자율 실행에는 목표, 예산, 멈출 조건을 사용자와 먼저 정해야 했다. 검증 기준은 목적에 비해 과하지 않은지 따져야 했다.

## 6. 구현·운영 실수
- 로컬 테스트는 통과했지만 Kaggle로 보낸 묶음에서 실패했다(EF L96).
- 장치 불일치로 8B 실행이 실패했다(EF L249).
- r3는 GPU 1,611.595초를 쓰고 측정 가능한 probe가 0개였다(EF L152, L156).
- smoke1에서 VisRef prefill OOM이 났다(EF L761). 직전 검토는 "명백한 버그 없음"이었다.
- 태그를 붙여 다시 주입하자 형식이 오염됐다. 두 번째 `</think>`가 63단계 중 31단계에서 나왔다(EF L774, L800).
- 보고서가 채점 버전이 섞인 값을 합산했다(EF L1114).
- 다른 세션이 채점기를 바꾼 사실을 기록하지 않았다(EF L1074). 이후 "VisRef 작업은 한 세션에서만" 규칙이 생겼다.
- 같은 이름의 실행 폴더를 덮어썼다(EF L963).
- 공개된 p값이 Python 버전에 따라 달랐다(EF L1601). 공개 재검증 명령을 한 버전에서만 확인했다.
- 반성: 실행하는 묶음 그대로 시험해야 했다. 지원한다고 적은 버전 전체에서 돌려 봤어야 했다. 실행 기록은 덮어쓰지 못하게 막았어야 했다.

## 7. 하위 에이전트·외부 AI의 숫자를 그대로 쓸 뻔했다
- LLM 답 추출을 시험할 때 Haiku 하위 에이전트가 36행 모두 빈 값을 냈다(EF L931).
- Gemini는 빈 응답에서 답을 지어냈다(EF L1232). 그래서 "응답에 있는 답만 인정" 규칙이 생겼다.
- 빈 추출을 그대로 채점해 정오가 2건 바뀌었다(EF L1450).
- 감사 하위 에이전트가 "시각 토큰 전부 주입"이라고 잘못 판정했다(`audit_summary_s1s4.md` L131).
- 같은 감사가 선택 편향 때문에 잡음을 과대평가했다(L132).
- 계획 검토의 수치가 Claude의 재계산과 달랐다(`plan_review_20261011.md` L16).
- 외부 피드백이 잘못된 분모로 계산한 41.8%를 냈다(EF L1407).
- 반성: 하위 에이전트와 외부 도구의 숫자는 Claude가 원자료로 다시 계산하기 전까지 "미확인"이다. 이번 문서도 같은 규칙으로 근거 줄을 대조했다.

## 8. 시간·비용 추정이 크게 빗나갔다
- st_official을 "문항당 약 4분"으로 추정했다(EF L1152). 실제로는 컨텍스트 상한 근처 문항이 4.7–5.6시간 걸렸다(EF L1327). 결국 분석하지 못하고 삭제했다.
- fill을 "약 9–9.4시간"으로 추정했다(EF L1388). 실제는 약 11.3시간이었고(EF L1438), 24문항이 빠졌다. 외부 도구가 시간이 불확실하다고 경고했지만 "새 근거 없음"으로 기각했다(EF L1406).
- 반성: 추정은 비슷한 실행의 실측값으로 해야 했다. 불확실하면 여유를 크게 두고, 경고를 기각할 때는 근거를 남겨야 했다.

## 9. 어려운 말로 써서 읽히지 않았다
- 공개 문서가 "읽기 (a)~(f)", "grounded", "nat", "s1", "§", "모델 카드" 같은 기호와 업계 용어를 풀지 않고 썼다. 사용자가 몇 번이나 되물어야 했다(EF L1615, L1652).
- 반성: 읽는 사람 기준으로 써야 했다. 기호 대신 이름을, 용어 대신 뜻을 써야 했다.

## 지금 남아 있는 불일치 (고칠 것)
- 출처 대장 37·44행의 상태 열과 요약 집계는 여전히 "인용 구현에서 확인"이다. 감사 후 "가정"으로 바꾼다고 메모만 하고 표는 고치지 않았다(SPEC_LEDGER 37행·44행의 상태 열, 상태별 집계 표의 "인용 구현에서 확인" 줄, 감사 메모의 37행과 44·19행 항목. 표를 넣을 때마다 줄 번호가 밀려서(10-12 결정 대장 35줄, 10-13 J-23 2줄) 줄 번호 대신 행 이름으로 적음). 하위 에이전트가 발견했고 Claude가 원문으로 확인했다.
- 이 문서의 범주별 건수(하위 에이전트 집계 74건)는 Claude가 전부 대조하지 않았다.

## 재발을 막는 방법

### 무엇이 오류를 잡았나
하위 에이전트 집계(Claude 미대조)로는 사용자가 약 14건, 독립 검토 세션(다른 모델)이 약 17건, 외부 AI 피드백이 약 9건, 스모크 테스트가 3건을 잡았고 나머지는 자체 확인이었다. 2026-10-13에는 작업을 보지 않은 상위 모델의 독립 검토가 중간 수준 문제 5건과 낮은 수준 13건을 찾았다(`repro/audit/independent_review_20261013/review.md`). 즉 **다른 눈(사람이나 다른 모델)과 작은 시험**이 가장 잘 잡았다. 아래 방법은 이 두 가지를 정해진 절차로 만드는 것이다.

### 1. 결정 대장: 사용자 결정이 사라지지 않게 (1절 대응)
- 한 파일에 결정마다 한 줄: 번호, 결정 내용, 날짜, 결정한 사람, **코드·설정에서 어디에 반영됐는지(파일:줄 또는 설정 이름)**, **확인하는 테스트 이름**.
- 결정마다 테스트를 하나 둔다. 예: "Z = 마지막 층"이면 VisRef가 `last_hidden`으로 Z를 받는지 확인하는 테스트(이번 `tests/test_hs.py`가 그 예). 결정이 코드에서 빠지면 테스트가 실패한다.
- 코드를 새로 쓰거나 세션을 넘길 때, AI는 결정 대장 전체를 새 코드와 대조한 표를 먼저 사용자에게 보여 주고, 빠진 결정이 있으면 "빠짐"이라고 쓴다. 사용자는 그 표를 확인한 뒤에만 실행을 승인한다.
- **결정 값은 한 곳에만 둔다**: 코드 기본값이 곧 결정값이다. 실행 인자는 변형 실험에서 기본값과 다른 값만 넘긴다. 결정이 바뀌면 같은 변경에서 기본값, 결정 대장, 결정값 테스트를 함께 고친다.
- **변형이 본 설정이 되면 값을 옮긴다**: 변형으로 시작한 설정(예: b_test의 1,024 상한)이 본 실험 설정이 되면, 그 값을 실행 인자에서 코드 기본값으로 옮기고 인자에서는 지운다. 상한 기본값 문제는 바로 이 단계를 건너뛰어서 생겼다.
- **결정값 테스트**: `repro/tests/test_decisions.py`가 `run.py` 기본값이 결정값과 같은지 확인한다(적용함, 10-12). 상한도 10-13 기본값을 고친 뒤 이 테스트에 넣었고, "모든 생성 실행이 결정값을 인자로 넘겼는지"를 확인하는 테스트도 함께 둔다.
- **실행 묶음을 만들 때 실제 설정을 대조한다**: 기본값과 실행 인자를 합친 실제 설정을 결정 대장 값과 비교해, 다르면 변형 이름과 이유를 적어야 묶음이 만들어지게 한다(아직 안 함). 실제 설정은 지금도 실행 시작 로그에 기록되므로, 실행 뒤에도 같은 대조를 할 수 있다.

### 2. 가정 대장: 확인 안 된 가정 위에 결정을 쌓지 않게 (2절 대응)
- 다음 결정의 근거가 되는 가정은 따로 적는다: 가정, 상태(미검증 / 검증됨 / 반증됨), 이 가정에 기대는 결정.
- **"실행하지 않는다", "이 설명은 지지되지 않는다" 같은 결정은 검증된 가정에만** 기댄다. 미검증이면 먼저 작은 측정을 한다. 예: "채운 토큰이 관련성 순서인가"는 실제 데이터 몇 문항으로 순위 상관을 재 보면 GPU 없이 확인할 수 있었다.
- 가정이 반증되면 그 가정에 기댄 결정과 문장을 같은 날 모두 다시 연다.
- "같다", "그대로다"라는 주장은 대리 지표(예: 종료 방식 일치율)가 아니라 그 대상을 직접 비교한 값(예: 텍스트 일치율)으로 확인한다.

### 3. 문장마다 출처: 확인 없는 단정을 막게 (3절 대응)
- 수치나 사실을 담은 문장은 근거(파일:줄, URL, 대장 번호)를 붙여 쓴다. 근거를 그 자리에서 다시 열어 보지 않았으면 "미확인"이라고 쓴다. AI가 기억이나 이전 요약에서 가져온 내용은 기본이 "미확인"이다.
- 공개 문서는 자동 검사를 넓힌다. 지금은 README 숫자가 결과 파일과 맞는지만 보지만(`scripts/check_readme_numbers.py`), 근거 표시가 없는 수치 문장을 찾아내는 검사도 만들 수 있다.
- 지표를 해석하는 문장은 그 지표의 정의 줄(부호 규약, 분모)을 함께 인용한다. 예: "순위 상관 −0.171(음수 = 관련성 큰 것이 먼저, `dpp.py` L107-108)".
- 공개 전에는 **다른 모델에게 "근거 없는 문장과 과장된 문장만 찾아라"라는 검토를 맡긴다**. 쓴 모델과 다른 모델일수록 좋다(예: Claude가 쓴 문서는 Codex가, Codex가 쓴 문서는 Claude가). 이번 외부 검토가 5건을 찾은 것이 그 예다.

### 4. 해석 문구를 미리 정한다: 과장을 막게 (4절 대응)
- 사전등록 때 결과별 문구를 같이 정한다. 예: CI가 0을 포함하면 "이 표본으로는 약 X pp보다 작은 차이는 가려낼 수 없다", 논문 값을 포함하면 "논문 값과 양립(같다는 증명은 아님)".
- 검출력(가려낼 수 있는 최소 차이)을 결과와 함께 적는다. 표본이 작은 진단(예: 150문항)은 "결론 없음"이 기본이다.
- 쓰지 않을 말을 정해 둔다: "재현됨", "효과 없음", "~이 원인"(직접 시험하지 않은 경우).

### 5. 자율 실행은 계약부터: 범위 초과를 막게 (5절 대응)
- AI에게 실행을 맡기기 전에 목표, GPU 예산, 멈출 조건, 사용자에게 물어야 하는 지점을 적어서 합의한다.
- 검증 기준은 "이 질문에 답하는 데 필요한 만큼"으로 정하고, 기준을 통과하지 못하면 진단 실행을 더 붙이기 전에 사용자에게 알린다.
- 본 실행 전에는 짧은 파일럿(예: 20문항)으로 속도·오류·형식을 확인한다.

### 6. 실행 위생: 구현·운영 실수를 막게 (6절 대응)
- 실제로 보낼 묶음 그대로 테스트한다(이번에는 노트북 안의 코드 sha를 대조했다).
- 후속 실험이 본 실험 결과와 짝 비교를 한다면, 본 실험에 저장된 첫 단계에서 출발하거나 비교 상대를 같은 세션에서 다시 돌린다. 같은 시드만으로는 GPU 계산 차이 때문에 같은 텍스트가 나오지 않는다.
- 지원한다고 적은 Python 버전 전부에서 `make check`를 자동으로 돌린다(GitHub Actions 같은 자동 실행).
- 실행 기록 폴더는 덮어쓰지 못하게 막는다(적용됨). 한 프로젝트는 한 세션에서만 다루고, 다른 곳에서 코드를 바꿨으면 기록에 남긴다.

### 7. 하위 에이전트·외부 도구 결과는 다시 계산한다 (7절 대응)
- 하위 에이전트에게는 근거 줄 인용을 필수로 요구한다.
- Claude는 그 인용과 숫자를 스크립트로 원문과 대조하고(이번 문서의 57곳 대조처럼), 일치하기 전까지 "미확인"으로 둔다.

### 8. 시간 추정은 실측으로 (8절 대응)
- 같은 설정의 파일럿 실측으로 추정하고, 30% 이상 여유를 둔다.
- 외부 경고를 기각할 때는 기각 근거를 숫자로 남긴다.

### 9. 쉬운 말 (9절 대응)
- 기호(읽기 (a), §) 대신 이름을, 업계 용어(모델 카드, nat) 대신 뜻을 쓴다. 꼭 필요한 용어는 처음 나올 때 풀어 쓴다.
- 공개 전에 사용자가 한국어판을 읽고, 막히는 곳을 표시한다.

### 사용자가 AI에게 던지면 좋은 질문 다섯 개
1. "그 문장의 근거 줄은?"
2. "그건 검증된 거야, 가정이야?"
3. "이전에 내가 정한 결정과 코드(기본값 포함)를 대조했어? 빠진 것은?"
4. "이 결정이 기대는 가정은 뭐고, 그게 틀리면 무엇이 바뀌어?"
5. "이 표본으로 가려낼 수 있는 최소 차이는?"
